## Top of Mind for Founders & Leaders

<!-- fnr:top_of_mind -->
**From bottoms-up to the enterprise, for a technical product.**  An engineer or agent finds your open-source project, or tool, installs it and starts calling it.  Inbound follows.  The hard part is the step after: how to organize the inbound, and calibrating across deal sizes especially with a small founder-led team.

- **Understand your usage patterns.**  This is about your pipeline efficiency, and how easily customers go from top of funnel to usage to conversion to paid, and then keeping a close eye on retention.  Understanding when the user sees the "aha" moment will help you optimize for it.  With agents, this pattern can grow fast, so signups can happen quickly, but then converting to paid, and retaining may be where you fight the battle.
- **Productize the deployment, not each deal.**  For on-premise deals, try to home in on 1-2 configurations (e.g. AWS, or GCP).  Document a reference architecture, and turn every other ask into a scoping question.  Keep one technical pack, templated per call, with pricing, the deployment, the security answers and the questions that size the work.  Price deployment explicitly, even when you waive it.
- **Founder-led, Product-led, then hire sales to scale.**  Ideally the product speaks for itself, and usage happens because of immediate value the engineer or agent finds.  With enterprise deals, this is more complicated with more factors, and complexity.  Once you've done a few of these, you can figure out how to scale, and then identify the right type of sales person you need, likely an engineer who can deploy and sell, a forward-deployed or solutions engineer.  Hopefully this is about volume management, not trying to find a market for your product.

Select reading: [CRV on FDEs](https://www.crv.com/content/forward-deployed-engineer) and [First Round's Founder-led sales at Merge](https://review.firstround.com/merges-path-to-product-market-fit/).

## Interesting Tech

<!-- fnr:tech -->
- **What a "software factory" actually is** — a team-level system: work comes in from a queue (a ticket, Slack, CI or a schedule), agents run unattended in isolated sandboxes, and pull requests come back through a review gate under the team's controls.  That pipeline and those controls are what separate it from a coding agent (one harness doing one task), an IDE agent (a person in the loop on one machine) or an orchestration library.  No single product does all of it, so each kind of provider covers a different piece:
  - **Factory platforms** run many agents under one set of controls.  [Warp Factories](https://www.warp.dev/factories) defines a factory in a config file, runs any MCP-capable agent (its own, Claude Code, Codex, Cursor) with a model per stage, on its cloud or yours, and prices per run.  [8090](https://www.8090.ai) is a hosted control plane over third-party agents, and [Tessl](https://tessl.io) builds up from skills to loops to a factory.
  - **Autonomous engineers** are the agent itself, sold as a teammate.  [Devin](https://devin.ai) runs parallel cloud sessions and has its own review product.  [Factory](https://factory.com)'s Droids switch between models and deploy anywhere from SaaS to air-gapped.  [GitHub Copilot's cloud agent](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent) goes from an issue to a draft PR inside Actions, and [Cursor's cloud agents](https://cursor.com/docs/cloud-agent) run in isolated VMs launched from Slack, GitHub, Linear or an API.
  - **Open-source orchestrators** let you assemble your own.  [Gas Town](https://github.com/gastownhall/gastown) (MIT, Go) manages a workspace of many agents, [OpenHands](https://github.com/OpenHands/OpenHands)' Agent Canvas can run Claude Code and Codex as subprocesses, OpenAI's [Symphony](https://github.com/openai/symphony) is a spec plus a prototype tied to Codex, and StrongDM's [Attractor](https://github.com/strongdm/attractor) is specs only, with no code.
  - Platform versus agent is a spectrum, not two camps: Factory, OpenHands and Cursor sit on both sides.  And the team, not just the vendor, now sets which tools the agents get: Factory and Devin both let admins run their own allow-listed tool marketplace.
- **[Elephant-Goldfish Model](https://github.com/google/elephant-goldfish-model)** (Google, Apache-2.0; not an officially supported Google product) — a plugin for Claude Code, Codex, Antigravity and ChatGPT that separates writing a design from reviewing it.  A long-context agent (the elephant) drafts the spec, then fresh subagents with none of that context (the goldfish) review it in stages before any code is written, ranking findings as Blocker, Major or Nit, and a drift report later checks the code against the spec.  The bet is that a reviewer who didn't share the session catches the unstated assumptions the author can't see.
