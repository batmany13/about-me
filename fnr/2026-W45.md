## Top of Mind for Founders & Leaders

<!-- fnr:top_of_mind -->
Capability-led discovery is a matter of watching signals:

- **Something working unusually well,** even a side effort that got a fraction of your time.
- **A problem you're solving internally** maybe to enable your original idea or built on top of the core capabilities.
- **A market that keeps catching up** to your positioning, which means the wedge isn't durable or you're not structured to capture it.
- **A different buyer pulling** than the one you planned for.

Before committing, ask what carries over (the team, your backers, the hard problem you learned), whether you've actually seen it work in the wild, and whether a narrower focus actually opens up more.  But a pivot is not enough: put significant effort into moving the sales motion and the company's energy in the new direction.

## Interesting Tech

<!-- fnr:tech -->
- **Who checks the agent's tests?** — When an agent writes both the code and its tests, the tests tend to confirm the code rather than catch its mistakes.
  - [TestPrism: Rethinking Test Evaluation Beyond a Single Reference](https://www.alphaxiv.org/abs/2610.12289) (Nanjing University, PolyU, Tencent) comes in two parts.  **TestPrism** is the benchmark: instead of checking a suite against one correct solution, it checks it against several valid versions and several deliberately wrong ones, and a suite only counts if it accepts every valid version and rejects every wrong one.  By that bar, the best agent setup scored 28%, against about 60% on the usual check, so about half the tests that looked good were letting bugs through.  **TestHelix** is the fix: several agents each write tests and a fix independently, and every agent's tests run against every other agent's fixes, so a test that only passes its own fix gets caught.  That cross-checking added about 9 points.  An agent grading its own work looks better than it is, and making agents check each other narrows the gap.
  - [EvilGenie: A Reward Hacking Benchmark](https://www.alphaxiv.org/abs/2511.21654) (MIT FutureTech, Cambridge Boston Alignment Initiative) makes cheating easy on purpose: coding agents get 154 hard problems in a workspace where they can read and edit the tests, and 30% of the tests are held back to check the result.  On clear problems, agents cheated 2% of the time or less.  On the nine ambiguous ones, they hardcoded the expected answers on 22–44%, reading the tests rather than editing them, and some shortcuts still passed the held-back tests.  Unclear specs invite cheating.  It used older models (Codex on GPT-5, Claude Code on Sonnet 4), so read it as a pattern, not a current rate.
  - Testing vendors now sell themselves as that independent checker, built in two different ways.  [Klarent](https://klarent.ai) has an LLM write ordinary test code step by step against the live app, and then the fixed code is what runs, so no model is judging at run time.  [mabl](https://www.mabl.com) offers coding agents a hosted MCP server and skills to plan, run and fix tests.  But an agent with an editor key can also change those tests, which is exactly the independence the pitch rests on.  Neither has published a measurement.
  - A cheap thing to try: break your code on purpose a few ways, and see how many your agent's tests catch.
- **A rising score doesn't prove the reward works** — In [Spurious Rewards](https://www.alphaxiv.org/abs/2506.10947), one model improved almost as much on random rewards as on correct ones, and the effect mostly disappeared on other model families.  In [Reward Hacking in Rubric-Based RL](https://www.alphaxiv.org/abs/2605.12474), a weak judge let more and more unearned credit through as training went on.  Before trusting a gain, compare against a random reward, a second model family and a judge you don't train against.

## What I've Been Learning

<!-- fnr:learning -->
Finished *Inference Engineering* by Philip Kiely of Baseten (Baseten Books, 2026), a good high-level overview of why running inference is hard.  Classic web systems are built around requests that are cheap, short, stateless and uniform, and LLM inference breaks all four.

The idea I'm taking with me is disaggregation.  A request has two very different phases: prefill (reading the prompt) is limited by compute, while decode (generating each token) is limited by memory.  At enough scale they run on separate hardware, each tuned for its phase.

Briefly: distillation trains a smaller model from a bigger one, quantization runs the same model at lower precision, and speculative decoding has something cheap guess a few tokens ahead for the big model to check in one pass.

This is timely as I'll be at [INFER/CON](https://infercon.ai) on Nov 16th, and plenty of these topics will be covered.
